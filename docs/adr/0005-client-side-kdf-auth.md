# 0005 — Dérivation de la clé d'authentification côté client
**Statut** : accepté (2026-10-15)
**Contexte** : Cloudflare Workers plan gratuit = 10 ms de CPU par requête et PBKDF2 plafonné à 100 000 itérations. Mesure locale (workerd) : ~60 ms de temps réel pour un PBKDF2 100 000 → il serait très probablement coupé en production (erreur 1102). Argon2/bcrypt sont exclus (trop coûteux).
**Décision** : le mot de passe ne quitte jamais l'appareil. Le client calcule `auth_key = PBKDF2-SHA256(password, sel = "kortex-auth-v1:" + e-mail normalisé, 600 000 itérations)` (WebCrypto natif, ~200 ms dans un navigateur) et n'envoie que cette clé (`auth_key`, 43 caractères base64url, + `kdf: 1`). Le Worker en stocke un PBKDF2 léger (`PBKDF2_ITERATIONS`, 5 000 par défaut, sel aléatoire) : une fuite de la base oblige à refaire le KDF lent côté attaquant pour chaque hypothèse de mot de passe. La politique de mot de passe (longueur ≥ 10, liste de mots courants) vit dans `services/shared/src/auth.ts` puisque le serveur ne voit pas le mot de passe.
**Alternatives** : PBKDF2 100 000 côté Worker (risque 1102 sur le plan gratuit) ; Argon2 en wasm côté Worker (CPU) ; OPAQUE/SRP (plus sûr mais lourd à implémenter et auditer, à reconsidérer plus tard).
**Conséquences** : tout client (site, desktop, CLI) doit utiliser `deriveAuthKey` ; le champ `kdf` permet de migrer la dérivation sans casser les comptes ; la même racine pourra dériver une clé de chiffrement distincte pour Kortex Sync de bout en bout (sel différent). Un attaquant qui modifierait le JS du site pourrait voler le mot de passe, comme avec tout mot de passe saisi dans une page web (CSP stricte + SRI prévus).
