# 0025 — Proxy réseau et broker OAuth : routes du Worker de compte
**Statut** : accepté (2026-10-19), demande de l'utilisateur (« étape 3 » : proxy réseau authentifié et broker OAuth, V8). Complète MASTER_PROMPT §Connecteurs ; compatible avec RULES 3.5 (Workers TypeScript).
**Contexte** : Flow web a besoin d'un proxy (CORS) réservé aux connectés, rate-limité, avec liste blanche de connecteurs et un mode libre limité ; certains fournisseurs OAuth exigent un secret client, donc un échange de code côté serveur. La session, les limites de débit (D1) et la protection CSRF vivent déjà dans le Worker `api`.
**Décision** :
- `POST /v1/proxy`, `GET /v1/oauth/providers`, `POST /v1/oauth/exchange`, `POST /v1/oauth/refresh` sont des routes du Worker `api` (pas de nouveau Worker : pas de second contrôle de session, même quota gratuit). Le découpage en Workers séparés reste possible plus tard sans changer le contrat.
- Proxy : session par cookie obligatoire (jamais de jeton d'appareil : le desktop fait ses requêtes natives). HTTPS, port 443, pas d'identifiants dans l'URL, nom DNS public seulement (refus des IP littérales v4/v6 sous toutes leurs écritures, des noms à un seul label, de `.local/.internal/.lan…` et de `kortex.site` et ses sous-domaines). Chaque redirection est revalidée (3 au plus, uniquement pour GET/HEAD) et les identifiants ne suivent pas un changement d'hôte. Mode **connecteur** (liste `PROXY_CONNECTORS`, par défaut GitHub, Google APIs, Telegram, Discord, Slack, Notion, Dropbox, Microsoft Graph) : tous les verbes, en-têtes `authorization`, `x-api-key`, `content-type`, `notion-version`, corps ≤ 200 Ko, réponse ≤ 2 Mo, 120 requêtes/heure ; mode **libre** : GET/HEAD, aucun identifiant, réponse ≤ 1 Mo, 30 requêtes/heure ; dans les deux cas 20 requêtes/minute, délai 10 s. Les cookies de session ne sortent jamais, `Set-Cookie` n'est pas relayé, seuls quelques en-têtes de réponse passent. Réponse en enveloppe JSON (statut, en-têtes, corps en base64).
- Broker OAuth : fournisseurs fixes dans le code (GitHub, Google, Notion, Dropbox, Slack, Discord), actifs seulement si les secrets Worker `OAUTH_<NOM>_ID`/`_SECRET` existent. `redirect_uri` : origine autorisée de nos apps ou boucle locale (`127.0.0.1`, RFC 8252). Les jetons sont renvoyés à l'utilisateur sans être stockés ni journalisés ; seuls `access_token`, `refresh_token`, `expires_in`, `token_type` et `scope` sont relayés.
**Conséquences** : aucune clé fournisseur n'est configurée aujourd'hui (le broker répond « indisponible » partout) ; aucun client ne consomme encore ces routes (nœud HTTP de Flow à venir) ; le déploiement en production reste soumis à autorisation.
**Alternatives** : Worker `proxy` séparé (écarté : session et limites dupliquées) ; proxy ouvert (écarté : SSRF et abus).
